# S6819161 罗格朗门禁：新增证据与现场调查方案

> 更新：2026-11-25。承接[型号与手册核验](legrand-intercom-identification-and-manuals.md)及[ESP 桥接研究](legrand-esp-intercom-bridge-research.md)。目标：保留本户原室内屏，研究来电通知、主动监看和用户主动的一次开门，并分别验证米家、HA 的入口。本轮仅查公开资料，没有接线、抓现场包、运行第三方固件或操作门锁；现场项目均为 `not_run`。

## 1. 本轮结论与推荐顺序

**截至本轮仍未找到 S6819161 可直接使用的开源固件、接线图或已确认适用的完整手册。** 本轮新增两条具体线索：

1. **国内罗格朗有第三方终端工程集成的公开记录。** 金茂智能魔镜文档描述 LAN 对讲、罗格朗服务器向第三方同步地址本、终端按户号绑定。这比不同品牌 ESP 总线教程更贴近本项目，但文档没有标明本机系列，也没有开放协议或 SDK。
2. **ESP32 实验设备进入米家存在公开代码。** 一个社区 BLE 工程描述门窗状态经网关上报、插座属性经手机蓝牙控制。不过后者明确不经网关，不能据此实现离家远程开门；本轮核读的示例未提供罗格朗协议、继电器执行或视频实现。

因此建议同时推进两条调查：**核本小区的原厂云对讲／第三方终端支持；在确认网口电气条件后，记录本户原屏通信。** 视频和会话先在电脑／Linux 上验证，确认是简单事件／控制后再评估缩成 ESP。现在不依据“带 RJ45”或“能绑定米家”采购改造板。

## 3. 不改接线即可先完成的核对

本机已知：背标 `S6819161`，纸质简页 `LE13416AA A3`，RJ45 与 MAC 标签，两组红黑线。不能把照片上的 `12V` 当整机输入，也不能把红黑颜色当电压／用途证明。

| 需取得的信息 | 用途 | 当前状态 |
|---|---|---|
| 本机“关于／本机信息”的型号、软件和 PCBA 版本 | 建立背标与销售系列、软件版本的对应关系 | `not_run` |
| 实际“设置 → 说明书”二维码得到的下载 URL | 获取本机资料，避免继续套凯蕴手册 | `not_run` |
| 是否有绑定 App、云对讲、呼叫转移菜单；指定 App 名称 | 核原厂入口及是否需要小区服务 | `not_run` |
| 无人呼叫时，原屏主动监视和开门的行为 | 判定目标是否已有原机能力可供集成 | `not_run` |
| 两组红黑线的端子编号、去向、上游电源规格；RJ45 上游设备与供电定义 | 决定能否串接标准交换机及需要何种供电路径 | `not_run` |

可给安装商的核对清单（仅供用户转交，本轮没有外发）：

1. 请提供 S6819161、随附 LE13416AA A3 对应的销售型号、接线图和完整操作手册。
2. RJ45 是否标准 10/100/1000BASE-T？是否含标准 PoE 或专用供电？两组红黑线分别接哪个端子、用途和额定电压是什么？
3. 本项目是否开通原厂手机云对讲？需什么 App、账户／住户绑定、授权或扩展模块？支持无人按铃时监看和开门吗？
4. 是否支持第三方室内终端／地址本对接？有正式 SDK、网关或接口说明吗？能否作为本户附加终端，保留原屏同时工作？
5. 视频、来电事件、一次开门分别开放什么接口？是否只在呼叫期间有效？支持几路会话、有无超时和占线限制？
6. 本户允许的接入点在哪里；新增终端或交换机是否需要工程配置？不请求其他住户的账户、地址本或权限。

## 4. 条件方案：先用电脑调查本户以太网

以下只有在**确认标准以太网及供电路径兼容**后才适用。若有未知／专用供电或专有总线，先停止普通交换机方案，取得准确接口资料。

```text
本户楼宇来线 ── 独立测试交换机 P1 ↔ P2 ── 原罗格朗屏
                           │
                     P2 双向端口镜像
                           ↓ P3
                    USB 网卡＋笔记本
                           │
                 后续只输出解析后的应用数据
                           ↓ Wi-Fi
                    家庭网络／HA（待部署）
```

镜像阶段只观察原机正常工作。图中的家庭输出是后续阶段，**不是把两个网络建桥或开启共享上网**。原屏供电按已核实的原路径保留；若供电通过来线传递，必须另有完整匹配方案，不能假定普通交换机透传供电。

### 4.1 调查器材怎样选

| 器材 | 必需能力与用途 | 选择状态 |
|---|---|---|
| 独立管理型交换机，或合适 TAP | 镜像原屏端口的接收与发送；匹配实际速率、标签、组播和供电条件 | 条件候选，未采购 |
| 笔记本＋有线／USB 网卡 | 接镜像口，完整抓包、协议识别、验证媒体 | 优先复用现有设备 |
| Wireshark | 记录时间线、对端、信令与媒体 | 尚未连接现场 |
| ESP32＋以太网接口 | 后续实现已知且低流量的事件／控制协议 | 现在不选型 |

[TP-Link TL-SG105E 官方页](https://www.tp-link.com/us/business-networking/easy-smart-switch/tl-sg105e/)列出 5 个千兆口与 Port Mirroring，可作为研究器材类型的例子；仍须核实所购地区／硬件版本、双向镜像和实际配置。**这不是对本机供电或兼容性的推荐，也不增加现有家庭网络采购数量。**

只镜像原屏所在的 P2，一个源口双向复制通常已能覆盖该屏的进出通信；同时复制 P1 和 P2 容易记录重复包。镜像输出带宽须能承载两个方向合计流量。TAP 与交换机都要核链路协商、供电、掉电行为；新增串联交换机掉电会断原屏，监听电脑关闭通常不会，但均需现场验证。

镜像口不是默认的控制回传接口。后续主动拉流／开门若需发包，应先取得本户支持的接口和地址分配方式，再设计单独的通信端口，不能从“监听成功”直接跳到主动控制。

### 4.2 抓包设置与操作记录

1. 先配置独立交换机，仅接本户原屏链路。接线与供电由熟悉该系统的人按已确认资料完成，保留恢复原连接的方法。
2. 监听网卡不配置楼宇侧 IP，不启用 DHCP 客户端、IPv6 自动配置、网络发现、桥接或 Internet 共享；实际设置按测试电脑系统确认。无 IP 不代表绝对无发包，需要严格收包隔离时选支持该功能的镜像／TAP。
3. Wireshark 选择该网卡，启用混杂模式、完整包长；初次不按猜测的 SIP／RTSP 端口设抓取过滤器。镜像口只来自本户原屏端口，不扩大到楼栋上联。
4. 每个场景独立保存短文件，记录开始／操作／结束时间（北京时间）。若出现丢包，先解决镜像带宽、网卡或缓冲，不在残缺流量上断言视频加密或协议不支持。
5. 先用 `Statistics → Protocol Hierarchy / Conversations` 看通信，再按观察到的 MAC／IP 分析；单用 `eth.addr == <原屏MAC>` 的显示条件可能遗漏发往组播地址的视频。按已识别的会话关联流量。

| 文件建议名 | 用户在原屏上的操作 | 要回答的问题 |
|---|---|---|
| `01-idle.pcapng` | 待机约 1–2 分钟 | 是否有地址获取、注册、心跳、服务器联系 |
| `02-ring-no-answer.pcapng` | 本户正常呼叫，暂不接听，观察结束 | 铃响时是否已有视频；呼叫与停止对应哪些消息 |
| `03-answer-hangup.pcapng` | 接听、短暂通话、挂机 | 媒体何时启动；音频是否双向；结束后是否停流 |
| `04-idle-monitor.pcapng` | 无人呼叫时按原屏监视，等待自动结束 | 是否新建会话；能看多久；是否必须依赖原屏保持在线 |
| `05-user-unlock.pcapng` | 用户现场确认后在原屏主动开门一次 | 在待机、监视、通话中哪些状态允许动作；哪些消息只是应答 |

可重复的监视／呼叫用多次记录比对；不要把不同会话中的地址、计数或令牌误当固定命令。开门由用户按需要逐次操作，不自动循环、不重放抓到的报文。本轮不执行这些步骤。

原始包、视频、住户标识和认证数据保存在仓库之外。共享研究记录只需脱敏后的协议名称、时间关系、编码、端口类别和结论；不提交原始 PCAP、二维码、密钥或全量地址本。

### 4.3 如何把结果变成下一步

| 观察结果 | 应做的验证 | 硬件倾向 |
|---|---|---|
| 可稳定识别本户来电／挂机的少量未加密报文 | 先写离线解析，跨多次呼叫验证，再输出事件 | ESP 可成为候选；仍须实测镜像吞吐及丢包 |
| 明确有 SIP／SDP＋RTP | 核实际协商的编码、地址和端口；先验证已有会话的媒体 | Linux 优先；不是天然存在 RTSP URL |
| 原屏开时能取画面、关闭立即停流 | 查原厂是否允许附加终端／主动监视会话 | 只有临时画面时不能承诺随时观看 |
| 有本户授权的 RTSP 等独立媒体接口 | 单独验证待机取流、认证、时长和并发 | 可再接 HA／go2rtc；不必永久嗅探 |
| 私有 UDP 或未知封装 | 比对多次受控操作与媒体特征，先验证格式 | 电脑继续研究；不能把所有 UDP 强制解释成 RTP |
| TLS／SRTP 等加密，或没有可用媒体 | 转向原厂服务／正式终端接口 | 抓包本身不解决解密、会话或密钥问题 |
| 开门仅通话／监视时有效 | 接口文档确认会话约束；有支持时才能设计完整动作 | 模拟按键也继承同样限制 |

Wireshark 的 RTP 工具可以分析已识别的 RTP；没有列出 RTP 不证明没有音视频，可能因信令缺失、动态端口、私有封装或加密。看到可解码媒体也不等于具备独立建立会话的能力。

## 5. ESP 与米家如何进入最终方案

ESP 的候选位置是**匹配接口后的事件／控制处理器**。官方 ESP-IDF 提供以太网混杂模式和自定义接收路径，证明可以编写接收程序；它不保证原屏流量已到 ESP，更不等于已实现门禁协议。W5500 的 100 Mbps 网口与 32 KB 缓冲也不是 ESP 程序双向线速或视频不丢帧的保证。

米家最终必须逐项验收，不能以“设备出现在 App”代替：

| 路径 | 呼叫／事件 | 一次开门 | 视频／对讲 |
|---|---|---|---|
| 本机原厂云对讲 | 视具体型号与项目服务 | 视具体型号、状态与授权 | 视具体型号与服务；入口可能是原厂 App |
| 解析后进入 HA | 待本户协议验证 | 待本户动作接口验证 | 待本户媒体及会话验证 |
| 社区 ESP BLE 进入米家 | 有模拟状态上报案例；本户来电映射未做 | 所核插座例仅手机 GATT，未实现远程执行 | 所核项目未提供 |
| 真正米家设备事件经 HA 触发本户接口 | 可作为独立研究方向 | 缺可靠的主动操作识别、去重、重启不补执行和门禁端单次动作 | 不会自动产生米家摄像头／门禁页面 |

最后一行不能简单实施成“任意插座状态变成开门”：开机同步、自动化和故障恢复也可能产生状态变化，不能混同用户主动命令。本轮没有确认同时满足米家兼容、无源触点、点动和恢复行为的具体 SKU，因此不推荐采购；没有证据证明 Matter 可以自动把本机视频接进米家。

**进入实施的门槛：**本机手册／接口条件明确；原屏功能基线完成；取得可用事件／媒体／动作中的至少一项，并记录未支持的其余项；米家远控需要用手机蜂窝网络实际验证。HA、互联网或新增模块恢复时不得误触发开门，没有门磁反馈时只显示“开门指令”，不伪造“门已开／已锁”。
